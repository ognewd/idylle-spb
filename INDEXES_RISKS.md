# Риски добавления индексов в базу данных

## ⚠️ Риски и Overhead индексов

### 1. **Замедление операций записи (INSERT/UPDATE/DELETE)**
- При каждой записи/обновлении/удалении БД должна обновлять индексы
- **Влияние**: Замедление на 10-30% операций записи
- **Критично для**: Частых обновлений товаров, массовых импортов

### 2. **Использование дискового пространства**
- Каждый индекс занимает место на диске (обычно 10-30% от размера таблицы)
- **Влияние**: Увеличение размера БД
- **Пример**: Если таблица товаров 1GB, индексы могут добавить 200-300MB

### 3. **Время создания индексов**
- Создание индексов на существующих данных может занять время
- **Влияние**: Блокировка таблицы на время создания (для некоторых типов индексов)
- **Риск**: Простой приложения во время миграции

### 4. **Избыточные индексы**
- Не все индексы полезны - некоторые могут не использоваться
- **Влияние**: Overhead без пользы
- **Решение**: Анализировать планы запросов перед добавлением

## ✅ Когда индексы безопасны и полезны

### Безопасно добавлять если:
1. **Таблица редко обновляется** (товары обновляются нечасто)
2. **Много операций чтения** (каталог просматривают часто)
3. **Медленные запросы** (уже есть проблемы с производительностью)
4. **Маленький объем данных** (<10,000 записей - индексы создаются быстро)

### Осторожно если:
1. **Частые массовые обновления** (импорты из Мой склад)
2. **Большой объем данных** (>100,000 записей - долгое создание)
3. **Критичные операции записи** (нельзя допустить замедления)

## 📊 Анализ текущей ситуации

### Текущие индексы:
- `myWarehouseCode` - только один индекс
- Нет индексов на часто используемых полях

### Частота операций:
- **Чтение**: Очень часто (каталог, фильтры, поиск)
- **Запись**: Редко (добавление/обновление товаров через админку)
- **Массовые операции**: Импорт из Мой склад (периодически)

## 🎯 Рекомендации

### Безопасные индексы (добавить сразу):
```prisma
@@index([isActive])           // Используется в КАЖДОМ запросе
@@index([brandId])            // Частая фильтрация
@@index([isActive, brandId]) // Композитный для частых запросов
```

**Почему безопасно:**
- `isActive` редко меняется
- `brandId` не меняется после создания
- Эти индексы дадут максимальный эффект

### Индексы требующие анализа:
```prisma
@@index([price])              // Для сортировки и фильтрации
@@index([createdAt])         // Для сортировки "новые"
@@index([productType])       // Для фильтрации
```

**Почему осторожно:**
- `price` может часто меняться (скидки, обновления)
- Нужно проверить, действительно ли используются

### Не добавлять пока:
```prisma
@@index([name])              // Полнотекстовый поиск лучше
@@index([description])       // Полнотекстовый поиск лучше
```

**Почему:**
- Обычные индексы не помогут для `contains` поиска
- Нужен полнотекстовый поиск (GIN индекс) или Elasticsearch

## 📋 План безопасного добавления индексов

### Этап 1: Критичные индексы (безопасно)
1. Добавить `@@index([isActive])`
2. Добавить `@@index([brandId])`
3. Добавить `@@index([isActive, brandId])`

**Ожидаемый эффект**: Ускорение на 50-80% для основных запросов
**Риск**: Минимальный (поля редко меняются)

### Этап 2: Мониторинг и анализ
1. Запустить на проде
2. Мониторить производительность запросов
3. Проверить планы выполнения (EXPLAIN ANALYZE)

### Этап 3: Дополнительные индексы (если нужно)
1. Добавить индексы на `price`, `createdAt` если запросы все еще медленные
2. Использовать `CREATE INDEX CONCURRENTLY` для избежания блокировок

## 🔧 Безопасное создание индексов на проде

### Вариант 1: CONCURRENTLY (рекомендуется)
```sql
CREATE INDEX CONCURRENTLY idx_products_is_active ON products(is_active);
CREATE INDEX CONCURRENTLY idx_products_brand_id ON products(brand_id);
CREATE INDEX CONCURRENTLY idx_products_is_active_brand_id ON products(is_active, brand_id);
```

**Преимущества:**
- Не блокирует таблицу
- Можно создавать на проде без простоя

**Недостатки:**
- Дольше создается
- Нельзя использовать в транзакции

### Вариант 2: Через Prisma миграцию
```prisma
// schema.prisma
@@index([isActive])
@@index([brandId])
@@index([isActive, brandId])
```

Затем:
```bash
npx prisma migrate dev --name add_product_indexes
```

**Преимущества:**
- Версионирование
- Автоматическое применение

**Недостатки:**
- Может заблокировать таблицу на время создания

## ⚖️ Вывод

**Добавление индексов НЕСЕТ РИСКИ, но:**

1. **Для вашего случая риски минимальны**, потому что:
   - Товары обновляются редко
   - Много операций чтения
   - Индексы на `isActive` и `brandId` безопасны

2. **Рекомендация**: 
   - Начать с критичных индексов (`isActive`, `brandId`)
   - Мониторить производительность
   - Добавлять остальные постепенно при необходимости

3. **Альтернатива без индексов**:
   - Использовать кэширование (Redis)
   - Оптимизировать запросы (убрать лишние `include`)
   - Использовать материализованные представления

## 🎯 Итоговая рекомендация

**Добавить безопасные индексы** - польза значительно превышает риски для вашего случая использования.
