# Анализ масштабируемости архитектуры

## Текущая архитектура

### База данных
- **PostgreSQL** - хорошо масштабируется
- **Prisma ORM** - удобный, но добавляет overhead
- **Индексы**: Минимальные (только на `myWarehouseCode`)

### API запросы
- **Пагинация**: 24 товара на страницу (хорошо)
- **Фильтрация**: Множество полей (может быть медленно без индексов)
- **Поиск**: Текстовый поиск по нескольким полям (медленно на больших объемах)
- **Связанные данные**: Загружаются brand, categories, images, variants для каждого товара

## Оценка текущей производительности

### ✅ Что работает хорошо:
1. **Пагинация** - ограничивает количество загружаемых товаров
2. **PostgreSQL** - мощная БД, хорошо масштабируется
3. **Infinite scroll** - загружает данные постепенно

### ⚠️ Потенциальные проблемы:

#### 1. Отсутствие индексов на часто используемых полях
```prisma
// НЕТ индексов на:
- isActive (используется в каждом запросе)
- brandId (фильтрация по брендам)
- price (сортировка и фильтрация)
- createdAt (сортировка)
- productType, purpose (фильтрация)
```

**Влияние**: Запросы будут замедляться при росте данных

#### 2. Текстовый поиск без полнотекстового индекса
```typescript
// Текущий поиск:
{ name: { contains: search, mode: 'insensitive' } }
{ description: { contains: search, mode: 'insensitive' } }
```

**Влияние**: Медленный поиск на больших объемах (>10,000 товаров)

#### 3. Загрузка всех связанных данных
```typescript
include: {
  brand: true,
  productCategories: { include: { category: true } },
  images: { ... },
  variants: { ... },
}
```

**Влияние**: Большой объем данных на каждый запрос

#### 4. Сложные фильтры по purpose
```typescript
// Множество OR условий для поиска в строке
purpose: { contains: ',' + p + ',' }
```

**Влияние**: Медленные запросы при фильтрации

## Оценка масштабируемости

### Текущее состояние (без оптимизаций):
- **10,000 товаров**: ✅ Работает хорошо
- **50,000 товаров**: ⚠️ Начнутся проблемы с производительностью
- **100,000+ товаров**: ❌ Значительное замедление

### С базовыми оптимизациями (индексы):
- **50,000 товаров**: ✅ Работает хорошо
- **200,000 товаров**: ⚠️ Нужны дополнительные оптимизации
- **500,000+ товаров**: ❌ Требуется серьезная оптимизация

### С полной оптимизацией (индексы + кэширование + поиск):
- **200,000 товаров**: ✅ Работает хорошо
- **1,000,000+ товаров**: ⚠️ Возможны проблемы при высокой нагрузке
- **5,000,000+ товаров**: ❌ Требуется архитектурные изменения

## Рекомендации по оптимизации

### 1. Критичные индексы (добавить немедленно):
```prisma
model Product {
  // ... существующие поля
  
  @@index([isActive])
  @@index([brandId])
  @@index([price])
  @@index([createdAt])
  @@index([productType])
  @@index([isActive, brandId]) // Композитный индекс для частых запросов
  @@index([isActive, price]) // Для фильтрации + сортировки
}
```

### 2. Полнотекстовый поиск:
```prisma
// Добавить GIN индекс для полнотекстового поиска
@@index([name], type: Gin)
@@index([description], type: Gin)
```

Или использовать PostgreSQL Full-Text Search:
```sql
CREATE INDEX products_name_fts_idx ON products USING gin(to_tsvector('russian', name));
```

### 3. Кэширование:
- **Redis** для кэширования популярных запросов
- **Next.js ISR** для статических страниц категорий
- **API Route caching** для часто запрашиваемых данных

### 4. Оптимизация запросов:
- Использовать `select` вместо `include` для уменьшения объема данных
- Ленивая загрузка изображений (только первое изображение)
- Оптимизация загрузки вариантов

### 5. Архитектурные улучшения:
- **Read replicas** для чтения (при >100,000 товаров)
- **Search service** (Elasticsearch/Meilisearch) для поиска
- **CDN** для изображений
- **Database partitioning** по категориям (при >1,000,000 товаров)

## Вывод

**Текущая архитектура может выдержать:**
- **~10,000-50,000 товаров** без оптимизаций
- **~200,000-500,000 товаров** с базовыми оптимизациями (индексы)
- **~1,000,000+ товаров** с полной оптимизацией (индексы + кэш + поиск)

**Рекомендация**: Добавить индексы на критичные поля - это даст максимальный эффект при минимальных изменениях.
