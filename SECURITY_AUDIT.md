# Аудит безопасности сайта Idylle

**Дата:** 2026-02-02  
**Область:** Next.js приложение, API, аутентификация, данные, зависимости.

---

## Критические уязвимости

### 1. API администраторов без проверки прав (`/api/admin/admins`)

**Файл:** `src/app/api/admin/admins/route.ts`

**Проблема:** Эндпоинты `GET` и `POST` **не проверяют** JWT администратора. Любой пользователь может:
- получить список всех администраторов (email, id, роли);
- создать нового администратора (POST с `name`, `email`, `password`).

**Риск:** Полный захват админ-панели, создание учётных записей с правами admin.

**Рекомендация:** Добавить проверку токена через `verifyAdminToken(request)` (как в остальных `/api/admin/*`) перед выполнением логики. Использовать общий хелпер из `@/lib/admin-auth.ts`.

---

### 2. ~~Fallback-секрет JWT в коде~~ (исправлено)

**Было:** Везде использовался `process.env.NEXTAUTH_SECRET || 'fallback-secret'`.

**Сделано:** В `@/lib/admin-auth.ts` добавлена функция `getJwtSecret()` без fallback. Все admin API используют её; при отсутствии `NEXTAUTH_SECRET` возвращается 500. В `admin/login/route.ts` при выдаче JWT также проверяется секрет. Логи с email в login убраны.

---

### 3. ~~Учётные данные CDEK в коде (fallback)~~ (исправлено)

**Было:** В `src/app/api/cdek/cities/route.ts` и тестовых скриптах использовались хардкодные fallback-значения для CDEK_CLIENT_ID и CDEK_CLIENT_SECRET.

**Сделано:** Добавлен хелпер `getCdekCredentials()` (`@/lib/cdek/credentials.ts`), который читает учётные данные из таблицы `Settings` (ключи CDEK_CLIENT_ID, CDEK_CLIENT_SECRET) или из переменных окружения; хардкодных значений нет. В админке добавлена страница «Доставка (СДЕК)» (`/admin/delivery`) и API `GET/POST /api/admin/cdek` (с JWT) для задания и сохранения учётных данных. Маршруты `/api/cdek/cities` и `@/lib/cdek/auth.ts` используют `getCdekCredentials()`; при отсутствии данных возвращается/бросается явная ошибка конфигурации.

---

### 4. ~~Логирование чувствительных данных~~ (исправлено)

**Было:** В admins/route.ts логировались полные детали ошибок (meta, stack), в admin/login — email и полный error, в products/[id] — userId, user.email, user.role.

**Сделано:** Везде заменено на логирование только `error.message` (без stack, meta, email, userId, DATABASE_URL). Отладочные console.log с чувствительными данными удалены.

## Высокий риск

### 5. ~~XSS через `dangerouslySetInnerHTML`~~ (исправлено)

**Было:** Контент из БД вставлялся в DOM через `dangerouslySetInnerHTML` без санитизации.

**Сделано:** Добавлена утилита `sanitizeHtml()` в `@/lib/sanitize.ts` на базе `isomorphic-dompurify` (DOMPurify для SSR и клиента). Whitelist тегов и атрибутов (p, strong, a, ul, img и т.д.; без script, iframe, on*). Все места вывода HTML из БД переведены на санитизацию: `ProductInfo.tsx`, страницы категорий (`catalog`, `aromaty-dlya-doma`, `vannaya-komnata`, `uyut-i-interer`), страницы CMS (`cookies`, `terms`, `privacy`, `delivery`, `about`), `CategoryContentEditor`, `PaymentMethodSelector`, редактор шаблонов рассылок (`admin/email/marketing/templates/[id]/edit`). `Breadcrumbs` не менялся — там вставляется только JSON-LD через `JSON.stringify`, не HTML.

---

### 6. Загрузка файлов (upload)

**Файл:** `src/app/api/admin/upload/route.ts`

**Что хорошо:** Проверка типа (`image/*`), размера (10 МБ), авторизация админа.

**Риски:**
- Расширение файла берётся из имени: `file.name.split('.').pop()` — при имени вроде `file.php.jpg` может получиться неожиданное расширение; лучше явно маппить MIME → расширение.
- Нет проверки содержимого (magic bytes); теоретически можно загрузить исполняемый файл с подходящим MIME.
- Файлы сохраняются в директорию, доступную по URL; нужно убедиться, что веб-сервер не выполняет скрипты из `uploads/`.

**Рекомендация:** Явный whitelist расширений по MIME, проверка magic bytes для изображений, запрет выполнения скриптов в каталоге загрузок (Nginx/другой веб-сервер).

---

### 7. Нет ограничения частоты запросов (rate limiting)

**Проблема:** Публичные эндпоинты (`/api/admin/login`, `/api/auth/register`, `/api/orders`, `/api/newsletter/subscribe`, `/api/search`, и т.д.) не ограничивают число запросов. Возможны:
- перебор паролей на admin login;
- массовая регистрация;
- спам заказами/подписками;
- нагрузка на поиск и БД.

**Рекомендация:** Ввести rate limiting (по IP и/или по пользователю) для логина, регистрации, заказов, подписки и тяжёлых API (поиск, фильтры). Варианты: middleware Next.js, Nginx, или отдельный сервис.

## Средний риск

### 8. Health-эндпоинт раскрывает структуру БД

**Файл:** `src/app/api/health/route.ts`

**Проблема:** Возвращает количество товаров, категорий, брендов. Для мониторинга это полезно, но даёт сторонним лицам представление о масштабе данных.

**Рекомендация:** Оставить только статус БД (connected/disconnected) и, при необходимости, версию приложения. Детали (количество записей) отдавать только с авторизацией или по внутреннему URL.

---

### 9. ~~Переменные окружения и .gitignore~~ (исправлено)

**Было:** В `.gitignore` не было `.env`; только `.env.local` и `.env*.local`.

**Сделано:** В `.gitignore` добавлена строка `.env`, чтобы файл с секретами не попадал в репозиторий.

---

### 10. Prisma и инъекции

**Оценка:** Запросы строятся через Prisma Client (параметризованные запросы). Прямых конкатенаций SQL в коде не видно — риск SQL-инъекций низкий при условии, что в фильтры не подставляются сырые строки из запроса без валидации.

**Рекомендация:** При появлении `$queryRaw` или `$executeRaw` использовать только параметризованные вызовы (`Prisma.sql`) и не подставлять пользовательский ввод в шаблон строки.

## Зависимости (npm audit)

Обнаружены уязвимости в транзитивных зависимостях (в т.ч. `@aws-sdk/*`, связанные с `@types/nodemailer` и др.). Уровень — high; не все имеют доступное исправление через `npm audit fix`.

**Рекомендация:** Выполнить `npm audit` и `npm audit fix`; для оставшихся — проверить CVE и обновить пакеты до версий с патчем или временно принять риск с документированием.
